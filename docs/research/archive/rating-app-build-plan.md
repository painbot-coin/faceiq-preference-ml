# Rating app — build plan (sub-process of the panel pilot)

*2026-07-24 · Expands Step 3 ("Tooling") and owner-checklist task 4 of
`panel-pilot-execution-plan.md`. This doc covers only the standalone rating web
app: stack, data flow, build steps, deployment, and how the data comes back to
this repo for analysis.*

**Status 2026-08-01: built, deployed, and has carried three studies.** Repo
`faceiq-rating`, live at <https://faceiq-rating.vercel.app>. Currently serving run 3's
4,800 hard pairs + 20 golds; previously 2,980 (run 2) and 120 (soft launch).

Two things were added after this plan was written, both documented in
`panel-pilot-runbook.md`: `CURRENT_STUDY_ID` scopes the queue and monitor to the active
study, so **the database is no longer wiped between runs**; and `buildQueue()` counts
in-flight reservations, which fixed run 2's 8–56 votes/pair spread down to 6–7.

**Use the production alias in the study link, never a per-deployment URL.** The
Vercel dashboard lists several domains for the same deployment and they do not

deployment, it looks live because it responds 200, and it will serve a frozen
build to raters forever.

## What it is (and is not)

A **throwaway, standalone** pair-rating page for Prolific raters. Separate repo,
separate Vercel project, separate database. It never touches faceiq-labs prod,
and it never does analysis — it serves pairs and records judgments. That's it.

**In scope:** pair viewer (two photos, forced choice + tie), keyboard shortcuts,
progress bar, consent + instruction screen, an always-available "view
instructions" button (task outline + 3 worked examples, so we don't send a
separate sheet), gold-pair seeding, response-time capture, one DB row per
judgment, Prolific completion-code redirect, a read-only results/monitor page.

**Out of scope:** user accounts (Prolific passes `PROLIFIC_PID` as a URL param —
that IS the rater identity), image hosting (photos load from existing public
blob URLs), any analysis or scoring (done here, in Python, afterwards).

## Stack decision

| Layer | Choice | Why |
|---|---|---|
| App | **Next.js + TypeScript**, single repo | No heavy computation; API routes are the whole backend. No separate Node service. |
| DB | **Prisma Postgres on Vercel** (new DB in existing org) | Isolated from prod by design; schema is 2 tiny tables; free/cheap tier is plenty for ~36k rows. |
| Hosting | **Vercel project** on `<name>.vercel.app` | **No custom domain** — raters arrive via the Prolific study link and never see/type the URL. |
| Pairs input | Static `panel-pairs.json` committed to the app repo | Generated by this repo's sampling script; blinded (no bucket/theta/VLM label), photo URLs point at public blobs. |
| Python | **None in the app** | Python lives in faceiq-preference-ml only: generates the pairs (upstream) and analyzes the judgments (downstream). |

## Data flow

```
faceiq-preference-ml (Python)                rating app (Next.js)            Prolific
─────────────────────────────                ────────────────────            ────────
select_pilot_pairs.py (extended, Step 2)
  └─> panel-pairs.json (blinded)  ────────>  served statically
      sample-meta.json (answer key,          rater judges pairs  <────────  study link w/
      stays HERE, gitignored)                  └─> judgments table            PROLIFIC_PID
                                             completion code     ────────>  rater paid
scripts/analyze (Step 6 gates)   <────────  export judgments.jsonl
```

The answer key (`sample-meta.json`: strata, thetas, VLM labels) **never enters
the app repo or its DB** — the app stays blinded; joining happens here at
analysis time. The only exception is a boolean `isGold` flag + expected answer
for the ~46 gold pairs, which the app needs for live QC.

## DB schema (all of it)

```prisma
model Session {
  id           String   @id @default(cuid())
  prolificPid  String
  studyId      String
  sessionId    String
  startedAt    DateTime @default(now())
  completedAt  DateTime?
  judgments    Judgment[]
}

model Judgment {
  id                String   @id @default(cuid())
  sessionId         String
  pairId            String
  choice            String   // "left" | "right" | "tie"
  responseTimeMs    Int
  presentationOrder Int
  isGold            Boolean  @default(false)
  createdAt         DateTime @default(now())
  session           Session  @relation(fields: [sessionId], references: [id])
}
```

Rater demographics are NOT stored here — Prolific collects them via screening;
we join on `prolificPid` during analysis.

## Steps, in order

1. **Generate the input (this repo, blocked on Steps 0+2 of the pilot plan).**
   Extend `scripts/select_pilot_pairs.py` to the ~3,000-pair panel strata; run it
   against the cleaned re-export. Output: blinded `panel-pairs.json` + gold list
   (pairId + expected answer for the ~46 Dit+Alex+Gemini-unanimous pairs).
2. **Create the repo + project.** New GitHub repo (e.g. `faceiq-rating`),
   `create-next-app` with TypeScript, new Vercel project linked to it, new
   Prisma Postgres DB in the existing Vercel org, `DATABASE_URL` as an env var.
3. **Build the rater flow.**
   - `/?PROLIFIC_PID=…&STUDY_ID=…&SESSION_ID=…` → consent + instructions screen
     (text drafted from the pilot-500 labeler UI, per pilot plan Step 1.2) →
     creates a Session row.
   - Task screen: two photos side by side, "who is more attractive?", left /
     right / too-close-to-call, keyboard shortcuts (←, →, space), progress bar,
     persistent "Instructions" button opening the sheet + 3 worked examples.
   - Each answer → one `POST /api/judgment` insert with response time and
     presentation order. Queue = assigned slice of pairs with ~5% golds shuffled
     in; left/right order pre-randomized in `panel-pairs.json`.
   - Final screen: Prolific completion code + redirect.
4. **Build the monitor page.** One password-gated read-only route: judgment
   counts, per-rater gold pass-rate, response-time distribution, tie rate.
   This is what we watch during the soft launch.
5. **Deploy + dry-run.** Deployed at `https://faceiq-rating.vercel.app`; run
   ourselves through it end-to-end via `/?test=1` → "Start a test session";
   verify rows land, timings recorded, completion redirect works. Test sessions
   carry `studyId = "test"` and are excluded from queue coverage and analysis.
6. **Soft launch** (pilot plan Step 6.1): 100 pairs × 12 raters on Prolific.
   Watch the monitor page; fix; full launch.
7. **Pull the data back.** One export script/route dumps `judgments.jsonl` +
   `sessions.jsonl`; commit/copy into this repo (e.g. `labels/panel-pilot/`),
   join against `sample-meta.json` and Prolific demographics, run the Step 6
   gate analysis in Python.
8. **Tear down.** After the pilot (and any Step 7 scale-up run, which reuses the
   same app), archive the export, pause the Vercel project, delete the DB.

## Estimate

2–4 dev-days including QC logic (unchanged from the execution plan). No new
spend beyond the existing Vercel org — no domain purchase, DB on free/cheap tier.
